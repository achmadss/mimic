# Mimic Context Engine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give a character a memory of how they *sound* and of what the user is still waiting on. Concretely: real dialogue from the source material, tagged and retrieved per turn, and open threads the bot is reminded to ask about — plus a conversation window that follows the topic instead of a fixed last-N.

**Architecture:** The loop is unchanged (turn → one Jev request → LLM → scheduled delivery). This plan adds **one new read path** into the same request: `respond` gathers a `TurnContext` (examples, open threads, a topic-scoped message window) *before* Jev sees the turn and *after* Jev has judged it, and hands the result to the prompt. The `examples` table is offline content — built once by a script that cuts exchanges out of a transcript CSV and tags each one with a single Jev Choice — and read at reply time by `(characterId, emotion)`. Open threads live on `conversations.unresolved`, the column doc 02 §1 already specifies.

**Tech Stack:** unchanged — TypeScript (strict, ESM) on Node ≥ 22, `better-sqlite3`, `zod` v4; tests on `node:test` + `tsx`. The ingest script adds no dependency: the CSV parser is 30 lines against a file that is already on disk.

**Spec:** `docs/05-context-engine.md` §5.1 (transcript ingest, example selection), §6 (unresolved items), §5 (tag/topic retrieval before semantic), §7 (invalidation); `docs/04-jev-and-llm.md` §1 (`turn_emotion`, `opens_thread`), §2 (`LLMOutput.openThread`); `docs/02-state-model.md` §1 (`ConversationState.unresolved`).

## Global Constraints

- Everything in the core-loop plan's Global Constraints still holds: no new runtime dependencies, all time through `Clock`, every state write commits in one `store.tx(...)` with its event, conversation id = `${characterId}:${platform}:${chatId}`.
- `npm test` and `npm run typecheck` must both pass at the end of every task.
- **The reply must never fail because optional context failed** (doc 05 §9). A missing example table, an empty bucket, an unreadable transcript: the turn proceeds without it. Nothing in this plan throws on the reply path.
- **`respond` stays the only writer of conversation context.** Examples are read-only at reply time; the ingest script never runs while the bot is serving a turn.

## Spec deltas (deliberate, keep the docs' intent)

- **`UnresolvedItem` has no `status` field.** Doc 02 §1 gives it `status: "open" | "resolved"`. Nothing reads a resolved item — it is never shown, counted, or retrieved — so the field would be written and never read. The stored list *is* the open set: an item is removed when it has been asked about, and expires on a TTL. Doc 02 §1 is updated to match.
- **Examples carry an emotion tag, not a scenario tag.** Doc 05 §5.1 asks for an emotion Choice plus a scenario Choice plus five behaviour Nouls. Only the emotion has a reader: `turn_emotion` is what the turn produces, so it is what selection can match on. A scenario tag could only be read if every turn also answered a `turn_scenario` question, and until emotion-only selection demonstrably picks the wrong voice there is nothing for a second axis to fix. The ingest is idempotent and offline — re-running it to add a tag costs minutes.
- **There is no Context Planner, and no summaries.** Doc 05 §2 has Jev choose a `horizon` and vote `relevant_<id>` on candidate summaries. Candidates are summaries, and summaries are the one thing this plan does not build: they need a batched LLM job whose only consumer would be the planner. Without them, `horizon` has nothing to choose between — four of its five values resolve to "a window of raw messages", which is a store query, not a judgement. So the window is **derived, not asked**: `recent_topic` when a topic is active and has enough behind it, `recent` otherwise. Task 2. The planner conditionally re-enters when summaries exist (`docs/superpowers/plans/2026-10-01-core-loop.md` "Next plans").
- **Examples are not retrieved on `followup_due`.** `turn_emotion` is a judgement about the user's turn, and a follow-up has no user turn. The profile and persona are always in the prompt, so a follow-up still sounds like the character — it just has no fresh example to lean on.
- **The example pool is bounded by `ORDER BY id LIMIT 40`, not by a random sample.** A seeded pick over a stable pool is reproducible: the same generation seed always selects the same examples, so a bad reply can be reproduced and explained. `ponytail:` re-query with `ORDER BY RANDOM()` if the pool is ever measured to be unrepresentative.

## Review Focus

1. **Ingest never touches the reply path.** Running the script must not change how a turn behaves, and a turn must not run the script. Task 4 is a separate entry point; Tasks 5–7 only read.
2. **A character with no examples still replies.** Every new-persona path (a JSON file added by the user) must work with an empty `examples` table. Test: Task 2 "an empty pool selects nothing", Task 7 "no examples is not an error".
3. **`opens_thread` must actually fire.** This exact question shape has failed twice (doc 04 §1: `follow_up` measured a 0.49 median and needed its own threshold). Task 8 measures the live rate; `openThreadThreshold` is the knob.
4. **An open thread is asked about once, then it is gone.** Never re-asked forever, never silently dropped before it is asked. Tests: Task 2 "asked threads are removed", Task 7 "asked thread is retired".
5. **The window must not starve on a fresh topic.** A topic that started one message ago must not blank out the conversation behind it. Test: Task 2 "a new topic keeps a floor of history".
6. **A broken LLM must not consume a thread.** Threads are retired only after the reply that asked about them was actually generated. Test: Task 7 "a failed generation keeps the thread open".

### Task 2: `context.ts` — the window, the pick, the open threads

**Files:** `src/context/context.ts` (new), `test/context.test.ts` (new)

Three pure functions and one store query. All of doc 05's resolution logic, in one file, testable without a database.

```ts
/**
 * Doc 05 §5: the "PC history drowning out the keyboard topic" problem, fixed without embeddings.
 * Messages since the topic began — but never fewer than a floor, because a topic raised one message
 * ago would otherwise blank out the conversation the character is replying into.
 */
export function contextWindow(
  conv: ConversationState,
  config: Config,
  fetch: (since: number) => { role: "user" | "bot"; text: string; at: number }[],
): { role: "user" | "bot"; text: string; at: number }[] {
  const since = conv.topicStartedAt ?? 0;
  if (!since) return fetch(0);
  const topic = fetch(since);
  return topic.length >= config.minRecentMessages ? topic : fetch(0);
}

/**
 * Doc 05 §5.1: a seeded draw so the same examples do not repeat every turn, over a pool the store
 * already bounded. Deterministic for a given seed, so a surprising reply can be reproduced.
 */
export function selectExamples(pool: Example[], limit: number, seed: string): Example[] {
  return [...pool].sort((x, y) => seededUnit(seed, x.id) - seededUnit(seed, y.id)).slice(0, limit);
}

/** Open, unexpired, most recent first, capped. */
export function openThreads(items: UnresolvedItem[], now: number, config: Config): UnresolvedItem[]

/**
 * The list to store after a turn: asked threads removed, a newly raised one appended, capped at
 * `unresolvedMax` (oldest dropped first).
 */
export function nextOpenThreads(
  open: UnresolvedItem[],
  opts: { asked: UnresolvedItem[]; raised: string | null },
  now: number,
  config: Config,
): UnresolvedItem[]
```

`nextOpenThreads` ignores a raised summary that duplicates an open one (normalized compare, the same hygiene `scheduleReply` already applies to repeated lines) and generates the id with `randomUUID()`.

**Tests:** window falls back to full history when the topic is young and stays topic-scoped when it is not; `selectExamples` is stable for a seed, varies across seeds, and returns `[]` for an empty pool; `openThreads` drops expired items and caps the list; `nextOpenThreads` removes asked items, appends a raised one, dedupes a repeat, and keeps the newest `unresolvedMax`.

### Task 3: Reading the transcripts

**Files:** `src/context/ingest.ts` (new), `test/ingest.test.ts` (new)

Pure functions over the CSV text; no filesystem, no network, so the whole shape is testable against fixture strings.

The file is `~/Downloads/rickmorty-transcripts/Rick-n-Morty.csv` (9618 rows, 39 episodes). Header is `,episode no.,speaker,dialouge` — the misspelling is in the file, not a typo here. `dialouge` fields are quoted and contain embedded newlines and indentation, so this needs a real RFC-4180 reader, not `split(",")`.

```ts
export interface TranscriptLine { episode: string; speaker: string; text: string }
export interface Exchange { characterId: string; episode: string; firstRow: number; lines: TranscriptLine[] }

export function parseCsv(text: string): string[][]          // quotes, doubled quotes, embedded newlines
export function transcriptLines(csv: string): TranscriptLine[]
export function normalizeSpeaker(raw: string): string      // "Rick:" → "rick", "Pickle Rick" → "pickle rick"
export function speaksAs(speaker: string, characterId: string): boolean
export function cutExchanges(lines: TranscriptLine[], characterIds: string[]): Exchange[]
```

- `transcriptLines` skips rows with an empty or 1-character `text`, collapses runs of whitespace, and keeps `episode` as the raw string (`episode no.` is not numeric across the file — 39 distinct values including `"10"` and `"2"`).
- `speaksAs` matches the character id as a **whole word** in the normalized speaker, so `"Pickle Rick"` and `"Toxic Rick"` both count as `rick` while a future character named `ann` does not swallow `"anne"`.
- `cutExchanges` walks consecutive same-episode runs in spans of `EXCHANGE_SPAN = 6` rows (doc 05 §5.1 asks for 4–8) and keeps a span when the target speaks at least `MIN_TARGET_LINES = 2` times. One span can yield an exchange for Rick *and* one for Morty — the doc's "a Rick-and-Morty exchange counts for both characters". Identical spans are deduped by normalized text, because the file repeats lines across episodes.
- `Exchange.firstRow` is the row index in the file, so `id = \`${characterId}:${episode}:${firstRow}\`` is stable across reruns and the insert can be `OR REPLACE`.

Also here, because they are content questions and not plumbing:

```ts
export const SCENARIOS_UNUSED = undefined; // see Spec deltas — no scenario tag
export function taggingQuestions(index: number): Record<string, JevQuestion>
export function readTags(answers: JevAnswers, index: number): { emotion: Emotion }
```

`taggingQuestions(i)` keys its one question as `e${i}_emotion`, a Choice over `EMOTIONS`, so a batch of exchanges is one Jev request with several independent questions. The instructions describe the exchange as `{ question: ..., exchange: [...] }` rather than pasting it into prose.

**Tests:** `parseCsv` on a fixture with a quoted multi-line field, a doubled quote, and a comma inside quotes; `transcriptLines` skips blanks; `speaksAs` accepts `"Rick:"` / `"Pickle Rick"` and rejects `"Rick Sanchez's Robot"`… no — it *accepts* that one too (`rick` is a word), which is correct; the reject case is a different character whose name merely contains the letters, e.g. `speaksAs("Brick", "rick")` is false. `cutExchanges` keeps a span where the target speaks twice and drops one where they speak once.

### Task 4: The ingest script, and running it

**Files:** `scripts/ingest-transcripts.ts` (new), `package.json`, `tsconfig.json`

A thin CLI over Task 3, plus the one thing that needs a network: Jev tagging.

```
node --import tsx scripts/ingest-transcripts.ts [--csv PATH] [--limit N] [--batch N] [--concurrency N] [--dry]
```

- CSV defaults to `~/Downloads/rickmorty-transcripts/Rick-n-Morty.csv`; `--limit` caps exchanges **per character** (default 400).
- Tagging batches `--batch` (default 4) exchanges into one Jev request and runs `--concurrency` (default 4) requests at a time — a small promise pool, `ponytail:`-marked, since the ingest is offline and the ceiling is only the API's rate limit.
- Targets come from `loadProfiles("characters")`, so adding a persona does not need a script edit.
- `--dry` prints the counts and the first exchange per character and writes nothing.
- Writes through `Store.saveExample`, which is `INSERT OR REPLACE`: rerunning is safe and is how a new tag gets added later.
- Progress to stderr, one line per batch. A batch that fails is logged and skipped, not fatal — a partial table is still useful.

`package.json` gains `"ingest": "node --env-file-if-exists=.env --import tsx scripts/ingest-transcripts.ts"`; `tsconfig.json` `include` gains `"scripts"`.

**Run it:** `npm run ingest -- --dry` first to check the exchange counts, then for real against the default DB, then confirm with `exampleCount()` and a spot check that Rick's `joking` bucket is not empty.

### Task 5: Jev — `turn_emotion`, `opens_thread`, and the open threads

**Files:** `src/jev/questions.ts`, `src/jev/state.ts`, `src/jev/decide.ts`, `src/config.ts`, `test/jev.test.ts`

Both questions join the existing `trigger === "user_turn"` block: `turn_emotion` is a judgement about the user's turn, and `opens_thread` asks whether *the user* raised something unresolved. Neither applies to a follow-up or an activity change, and `decide` must read neither on those triggers.

```ts
q.turn_emotion = {
  type: "choice",
  instructions: "What is the emotional register of `currentTurn` — the one `character` is reading?",
  criteria: {
    neutral: "Ordinary, matter-of-fact",
    excited: "Something good happened, or they are wound up",
    annoyed: "Complaining, irritated, picking a fight",
    sad: "Down about something, hurting",
    confused: "Lost, or did not understand something",
    joking: "Playing around, teasing, not serious",
    serious: "Pressing, or admitting something real",
  },
};

q.opens_thread = {
  type: "noul",
  // Same shape as `follow_up`, which measured a 0.49 median on the shared threshold and never
  // fired (doc 04 §1). Ask about a concrete unresolved *event* rather than "anything worth asking
  // about later" — the vaguer the question, the lower the model scores it.
  instructions: "Did the user mention something concrete that is still open — an event that has not happened yet, a plan, a result they are waiting on? 'interview tomorrow', 'waiting on the scan'.",
};
```

`JevStateInput` gains `openThreads: UnresolvedItem[]`; `buildJevState` emits `unresolved: i.openThreads.map((t) => ({ id: t.id, summary: t.summary }))` — the summary, not the row (doc 04 §1: "Jev sees summaries and candidates, never raw database rows").

`DecideContext` gains `openThreadThreshold`. In `decide`:

```ts
// user_turn only, like mood: a decision must never read an answer nobody requested.
const emotion = c.trigger === "user_turn" ? choice("turn_emotion", EMOTIONS, "neutral") : undefined;
...
emotion,
openThread: c.trigger === "user_turn" && yes("opens_thread", c.openThreadThreshold),
```

Config gains `openThreadThreshold: 0.6` with the same comment `followUpThreshold` carries, and `configFromEnv` gets `MIMIC_OPEN_THREAD_THRESHOLD` so Task 8 can tune it without a rebuild.

**Tests:** both questions are present on `user_turn` and absent otherwise; a confident answer becomes `emotion`/`openThread`; a torn one falls back to `undefined`/`false`; `followup_due` and `activity_changed` still produce `openThread: false`.

### Task 7: Wiring `respond`

**Files:** `src/im/respond.ts`, `test/respond.test.ts`, `test/helpers.ts`

The turn gains one gather step before Jev and one write step after the LLM:

```ts
const open = openThreads(conv.unresolved, now, config);          // pruned, capped, for Jev
const recent = contextWindow(conv, config, (since) =>
  store.recentMessages(conversationId, config.recentMessages, turn?.firstAt, since));
```

`recentMessages` gains an optional `since` (default `0`), a fourth `?` in the existing query. After `decide`, and only when the turn is actually generating:

```ts
const examples = decision.emotion
  ? selectExamples(store.examplesFor(conv.characterId, decision.emotion, config.examplePool), config.maxExamples, generationId)
  : [];
const askAbout = decision.topicAction === "ask" ? open.map((t) => t.summary) : [];
```

and after the LLM returns:

```ts
const next = nextOpenThreads(open, {
  asked: decision.topicAction === "ask" ? open : [],
  raised: decision.openThread ? (output.openThread ?? null) : null,
}, now, config);
store.tx(() => scheduleReply(..., next));
```

`scheduleReply` takes the list as a final argument and writes it in the same `saveConversation` it already performs for a topic switch — one write, one transaction, both fields. The retire/raise happens **after** `d.llm.generate` resolves, so a failed generation leaves every thread open: a thread is consumed by being asked, and nothing was asked.

The duplicate-line filter in `scheduleReply` and the `alreadyQueued` set are untouched; examples are prompt input, not continuity.

**Tests:** examples reach the prompt for a matching emotion and none are fetched on a follow-up; a thread asked about is gone from the stored conversation and a raised one is present; a thrown LLM leaves the stored list unchanged; a conversation with an empty `examples` table replies normally; the window is topic-scoped when the topic is old enough and full-history when it is not.

### What the live run actually found

Run 1 (four turns) answered `respondMode: "later"` on all of them, because the
routine engine had just moved Rick to `working` — no context is built when no
reply is being written, so the run verified nothing. Task 8's script needs an
idle character; the run was repeated against a temporarily flattened routine
(`characters/rick.json` restored afterwards, byte-identical).

| Finding | Measured | Fix |
|---|---|---|
| `opens_thread` fired on every turn, including "ok i'm back" | 0.88 / 0.78 / 0.87 / 0.76 | The question said "did the user mention" while the state also carried `unresolved`, so Jev answered about the conversation. Reworded to `currentTurn` and named the exclusion. After: **0.93 on the turn that raised something, 0.02–0.06 on the three that didn't** — so `openThreadThreshold` stays at 0.6, and the separation is the wording's doing, not the bar's |
| `topic_action: "ask"` never won, so threads were never retired | 0.15 against `continue` 0.45 | The option had no referent. The open threads are now in the question's instructions and in the `ask` criterion. After: fired on the first turn where the user raised nothing new, the reply asked about the thread, and the thread was gone |
| The LLM wrote a thread summary from the conversation | a message about a landlord inspection recorded "thesis defense thursday" | `nextOpenThreads` checks the summary against the user's own turn (4-character prefix overlap) and **falls back to the turn's own words** rather than dropping the thread |
| `neutral` is a thin bucket, so consecutive neutral turns got identical examples | 3–5 examples against 213 `joking` for Rick; the same three ids on two turns | Recorded in doc 05 §12. The fix is at ingest (a second tag, or rebalancing), not at retrieval |

## Skipped, and when to add them

- **The Context Planner** (`horizon`, `relevant_<id>`, `ContextItem[]`, budgets). Its candidates are summaries, and there are no summaries. Add with them, not before.
- **Summaries and long-term memory.** The one piece of doc 05 with no cheap version: a batched LLM job over closed topics, a `summaries` table, and a retrieval query. Add when a conversation has run long enough that the raw window is the binding constraint — that is also the moment the planner earns its questions.
- **Example scenario and behaviour tags.** See Spec deltas. Add with `turn_scenario` when emotion-only selection is measurably picking the wrong voice.
- **Keyword/topic scoring** (doc 05 §5 rung 2). The store query is currently `(characterId, emotion)`; scoring turns it into a ranking over the same rows. Add when the emotion buckets are too coarse to sound right, which the ingest makes cheap to detect.
- **Embeddings / vector search** (doc 05 §5 rungs 3–4). Not until keyword scoring is measurably insufficient.
- **The send rate limit.** Still outstanding from the core-loop plan; unchanged by this plan.
